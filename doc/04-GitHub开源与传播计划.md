# 04 · GitHub 开源与传播计划

## 1. 用可验证的体验吸引用户

项目名先保持 `video-to-grayscale`，便于理解用途。展示文案可采用：

> Turn videos black and white, locally. Preview first, batch convert, keep your originals.
>
> 在本机批量将视频转为黑白，先预览再导出，保留原文件。

以上含预览的文案在功能交付后使用。早期版本只写实际已有能力。

核心展示点按顺序：

1. 本地处理，不需要账号；安装完成后可离线使用。
2. 三步完成常用任务，结果保存在明确的位置。
3. 可视化队列、失败恢复、原文件保护。
4. 使用原生 FFmpeg，经过验证的平台可选硬件编码。
5. 能查看实际转换配置，便于复现和排查。

“隐私友好”“速度快”需要由网络行为和基准支撑；避免“最快”“无损”“无限大文件”“保证兼容”等无法验证的宣传。

## 2. README 的首屏设计

建议英文 README 为默认入口，提供明显的中文入口。只维护一份版本和支持矩阵的事实来源，避免两种语言的能力声明不一致。

建议顺序：

1. 项目名、一句话价值、演示 GIF/视频。
2. 3–5 个真实卖点，少量有效徽章。
3. Quick Start：支持环境、安装 FFmpeg、安装锁定依赖、启动、打开实际地址。
4. 一张完整 UI 截图与三步操作说明。
5. 支持矩阵：平台、输入范围、音频处理、HDR 限制。
6. 如何工作：本机浏览器 → 本机服务 → FFmpeg；说明拖拽会产生本机临时副本。
7. 常见问题和错误恢复：文件在哪、为什么体积变大、为什么 HDR 被阻止、如何清理暂存。
8. 实测性能与完整复现方法。
9. 路线图、贡献、许可证、第三方说明。

首屏应让用户快速回答：它做什么、视频会不会离开电脑、如何启动、做完去哪找。

## 3. 演示素材设计

建议制作一个 20–40 秒的流程演示：

- 0–5 秒：展示彩色/黑白对比，说明本地处理。
- 5–12 秒：选择 3 个文件、确认输出目录和预设。
- 12–20 秒：显示真实短片预览及批量队列。
- 20–30 秒：展示结果并打开输出目录。
- 30–40 秒：简短展示一次失败后的重试或依赖诊断，证明工具可用。

演示加速需要标注，不用剪辑后的时间冒充转码性能。素材使用自行生成或有明确许可的短片，不录入个人路径、真实私密文件和桌面通知。

使用生成脚本提供小型样例；大视频放在可选下载位置或用户本地，不塞入 Git 历史。初期无需独立营销网站，README 和 Release 已足够。

## 4. 开源工程基础

| 文件或能力 | 首次公开版本要求 |
| --- | --- |
| README.md / README.zh-CN.md | 从干净环境实测步骤、截图、范围和限制 |
| LICENSE | 项目自有代码建议 MIT，采用前确认贡献来源与归属 |
| CONTRIBUTING.md | 启动、检查命令、测试素材生成、提交约定 |
| SECURITY.md | 描述本地服务边界及私下报告方式，联系方式待维护者填写 |
| CHANGELOG.md | 按版本描述用户可感知的改动和兼容变化 |
| Issue 模板 | 故障：环境、错误码、复现；功能：场景、频率和替代方式 |
| PR 模板 | 问题、最终行为、验证、截图（界面变化时） |
| CI | 类型检查、必要单测、真实软件编码集成测试 |
| .gitignore | 原视频、暂存、输出、私密日志、依赖和构建产物 |

首版使用用户安装的 FFmpeg，不随包自动下载或捆绑二进制。若后续分发 FFmpeg，需要单独核对所选构建和依赖的许可及分发要求；这里不预判其具体义务。

## 5. 发布顺序

### 内部试用版

先让 3–5 名目标用户按 README 安装，记录首次转换成功率、耗时和卡点。不靠维护者远程代操作掩盖安装问题。

### 首次公开版

通过 03 的发布验收后再发布。版本说明包含：已支持范围、已知问题、演示、安装步骤、测试环境、反馈入口。

### 后续小版本

优先处理用户最常碰到的三个问题；每次发布提供可验证的改进。通过实际兼容测试后更新平台徽章和支持范围。

## 6. 传播渠道与内容

- GitHub 仓库：维护准确的 description、主题标签、演示和 Release。
- 中文技术/创作社区：围绕“如何在本机批量转换”分享完整操作和真实限制。
- 英文开源社区：用短演示和可复现基准介绍项目；遵守社区自推广规则。
- 技术文章：介绍浏览器文件路径限制、可靠本地队列、M2 编码对照等实际解决的问题。

建议主题标签：`ffmpeg`、`video-processing`、`grayscale`、`local-first`；平台标签随真实支持情况添加。传播内容在本地准备好后由维护者决定发布时间和账号，本文不执行发帖。

## 7. 衡量项目是否在变好

| 指标 | 用途 | 获取方式 |
| --- | --- | --- |
| 首次转换成功率 | 检查安装和主流程 | 自愿试用记录 |
| 从启动到第一份输出的时间 | 检查使用门槛 | 现场观察或自愿反馈 |
| 典型批次成功率 | 检查可靠性 | 测试矩阵与本地诊断 |
| 同类问题重复出现次数 | 找文档或产品缺口 | Issue 分类 |
| 外部用户能否独立贡献 | 检查工程门槛 | 贡献者反馈 |
| Release 下载、Star、Fork 趋势 | 观察传播效果 | 平台提供的统计；不当成活跃用户数 |

默认不加入埋点。先解决实际使用障碍，Star 只作为辅助结果指标。

## 8. 适合开放给贡献者的工作

在核心结构稳定后提供小而明确的任务：错误信息翻译、平台安装验证、额外测试夹具、键盘可访问性、文档修正。每个 Issue 写清复现步骤和完成标准，避免让新人从零猜设计。

不把“增加更多滤镜”作为默认增长方式；先证明已有用户可以稳定完成批量转换。
