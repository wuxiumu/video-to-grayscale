# 01 · 可行性与原计划评审

## 1. 总体判断

**技术可行，原计划不足以直接进入完整开发。** 原生 FFmpeg 适合作为转换核心；本地网页能够降低界面开发成本。主要缺口集中在文件访问、输出策略、任务可靠性和安装交付。

| 维度 | 判断 | 成立条件 |
| --- | --- | --- |
| 视频转黑白 | 高可行性 | 首版明确支持普通 SDR 视频，验证滤镜和编码结果 |
| Mac Air M2 本地使用 | 高可行性 | 确认本机 FFmpeg 构建、编码器能力和真实样本表现 |
| 大文件、批量处理 | 可行 | 目录直读或流式暂存，限制并发，处理磁盘不足和失败恢复 |
| 普通用户安装 | 中等 | 依赖诊断、清晰启动流程；后续再提供桌面安装包 |
| Windows/Linux | 架构可扩展 | 文件路径、进程终止、打开目录都需要平台实测 |
| GitHub 高关注度 | 无法保证 | 验证需求，展示差异化体验，持续维护和发布 |

## 2. 原计划必须修正的假设

| 原表述或设计 | 问题 | 优化决定 |
| --- | --- | --- |
| 网页选择文件后把真实本地路径给 Node | 普通浏览器不暴露真实路径，`File.name` 只有文件名 | 主入口采用启动时指定根目录、服务端列文件；拖拽采用流式本机暂存 |
| 本机磁盘读写，不占浏览器内存 | 浏览器预览、上传仍会使用缓冲，不能承诺零内存 | 不将整段视频读入 ArrayBuffer；大文件优先目录直读 |
| M2 比 WASM 快 10 倍以上 | 没有针对本项目输入、参数和机器的对照实验 | 宣传只写原生处理、支持硬件编码；倍率等实测后发布 |
| `h264_videotoolbox` 代表整个流程硬件加速 | 编码、解码、滤镜是不同环节 | 首版只承诺经过验证的硬件编码路径，解码加速后续单独评估 |
| 示例音频自动复制 | 命令缺少 `-c:a copy` | 显式选择音轨策略；兼容优先默认 AAC，提供条件复制 |
| 未装 FFmpeg 自动切 WASM | 引入两套运行时和不同文件、内存、部署约束 | 首版明确报缺失依赖并给安装指引，WASM 演示后置且独立 |
| 解析 stderr 获取百分比 | 面向人的日志不适合作为稳定协议 | 使用结构化进度；未知时长显示已处理时间，不伪造百分比 |
| 暂停任务 | 队列暂停与正在编码的进程暂停含义不同 | 首版只做“暂停队列”：当前任务继续，后续不启动 |
| 开源即跨平台可用 | 平台相关行为未设计和验证 | macOS 优先，其他平台达到验收门槛后再标支持 |
| Canvas + MediaRecorder 只能输出 WebM | 输出格式依赖浏览器能力，表述过于绝对 | 不作为本项目路线；不保留该绝对结论 |

浏览器路径限制依据：[MDN 文件输入](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/input/file)。
音频复制与进度接口依据：[FFmpeg 文档](https://ffmpeg.org/ffmpeg.html)。

### WASM 的准确定位

ffmpeg.wasm 官方 FAQ 提示原生性能优势及其输入大小限制；官方性能页使用的测试环境并非本项目的 M2，因此不能外推成固定倍率。也不应将某个 WASM 实现限制泛化为所有浏览器的统一内存上限。

来源：[官方 FAQ](https://ffmpegwasm.netlify.app/docs/faq/)、[官方性能测试](https://ffmpegwasm.netlify.app/docs/performance/)。

### 原安装示例

原计划把 Markdown 链接放进 shell 的 URL 参数，会导致命令无法按预期执行。README 应将 Homebrew 安装引导链接与命令分开，避免复制错误；已有 Homebrew 的用户可使用 `brew install ffmpeg`。本项目启动时不自动安装系统软件。

## 3. 最关键的产品取舍

### 保留

- 本地处理，无账号、无云端上传、安装完成后可离线运行。
- 原生 FFmpeg、单个和批量任务、串行默认、保留原文件。
- 简洁网页界面和清晰的导出位置。

### 补齐

- 文件导入真正可实现的流程。
- 短片试转、质量选择、音轨和不支持格式提示。
- 任务取消、失败继续、重试、刷新恢复和输出校验。
- 首次启动诊断、真实测试样本矩阵、安装文档。

### 后置

- WASM、桌面壳、多平台硬件编码器矩阵。
- 当前转码进程暂停/断点续转、并发调优、复杂调色。
- 在线视频下载、AI 处理、时间线编辑和云端任务。

## 4. 风险与验证方式

| 风险 | 影响 | 验证或处理 |
| --- | --- | --- |
| iPhone HDR/杜比视界 | 可能出现灰阶和亮度异常 | M0 识别；首版拒绝自动转换并说明需先转 SDR，后续独立做色调映射 |
| 硬件编码器存在但运行失败 | 任务中断 | 小样本试编码；仅明确编码器错误允许自动软件重试一次 |
| 硬编文件大或质量欠佳 | 速度快却不值得用 | 同一源文件比较质量、大小、耗时，质量参数按编码器分别配置 |
| 音轨/字幕丢失 | 用户误以为完整保留 | 提交前显示首版只导出主视频和首条音轨，字幕及额外流不保留 |
| 视频旋转、奇数尺寸、VFR | 方向、尺寸、音画同步异常 | 独立样本；不默认强制帧率，明确补边和旋转策略 |
| 本地 HTTP 可被其他网页访问 | 未授权读取或触发转码 | 回环绑定、会话鉴权、Origin/Host 验证、目录范围控制 |
| 磁盘不足、强制退出 | 残留文件或假成功 | 临时输出、完成后校验、启动恢复和显式清理 |

## 5. 是否值得做

值得先做一个聚焦 MVP。灰度滤镜本身很容易复现，真正值得用户安装的是“连续处理一批素材，每一步都可预期”。

[Shutter Encoder 官方介绍](https://www.shutterencoder.com/)已经提供较丰富的图像和色彩调整能力。因此本项目的差异化建议是更短的黑白转换流程、轻量本地网页和透明批处理体验；这是定位判断，尚需用户试用验证。
